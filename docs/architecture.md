# Architecture

## Components

- `apps/web/`: Vite + React + TypeScript client; role-specific workspaces and responsive layouts.
- `apps/api/`: Express REST API, session authentication, authorization, validation, rate limiting, and audit writes.
- `prisma/`: normalized SQLite and PostgreSQL schemas, checked-in SQLite migration, and deterministic synthetic seed data.
- `private-uploads/`: local-only, non-public document storage. Paths are generated by the server; upload content is not served by a static middleware.
- `tests/`: HTTP-level API integration tests against the seeded database.

The browser calls the same-origin `/api` path. Vite proxies it to the API in development. The API returns consistent JSON errors and independently enforces role and patient-resource authorization; client navigation is not an access-control boundary.

## Authentication and authorization

Passwords are hashed with bcrypt. Login issues a signed, eight-hour, HttpOnly, SameSite=Strict cookie backed by an expiring database session; logout revokes that server-side session. The role is reloaded from the database on every authenticated request; it is not accepted from browser input. Doctor access to patient records requires an existing patient-specific appointment or clinical record. Admin-only data endpoints have explicit role gates. Mutating browser requests are checked against an exact origin allowlist.

## Data and workflows

- Appointments persist in Prisma and are visible to the linked patient and clinician.
- Clinical notes become dated patient medical-record entries after the clinician submits them.
- Prescriptions contain explicit clinician-entered fields, are finalized by an authenticated doctor, and are associated with a patient record in one transaction.
- Follow-ups are doctor-created and patient-completable; creation and status changes are audited.
- OCR jobs keep processing/review status and extracted field JSON separate from human verification events. Each verification/rejection stores reviewer, decision, field states, and timestamp transactionally.
- Patient copilot sources are populated from records fetched for the signed-in patient. The doctor copilot requires an authorized patient ID and returns only records retrieved for that patient.

## Deliberate demo boundaries

The tested local path is SQLite. A PostgreSQL schema and local Compose service are included but Docker/PostgreSQL were unavailable for runtime validation here. OCR/provider queues are not asynchronous yet; the demo submission persists a private original and a clearly labelled empty draft. OCR service integration, image preprocessing, real structured-extraction schemas, LLM retrieval/generation, messaging, consent preferences, availability management, and full hospital operations are not configured. These omissions are listed rather than represented by fake success states.
